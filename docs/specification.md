# 非同期 UDP 通信プログラム仕様書

## 1. 目的

Windows、macOS、および Ubuntu Linux 上で動作する、非同期 UDP 通信向けのコマンドラインプログラムを開発する。

本システムは、常駐する UDP 通信サーバと、UDP パケットの送信をサーバに指示する送信指示クライアントの 2 プログラムで構成する。

## 2. 対象範囲

- C++ のスタンドアロン Asio（Boost 非依存）を使用する。
- IP プロトコルは IPv4 のみを対象とする。
- サーバの UDP 送信先および受信用待受ポートは JSON 設定ファイルで設定する。
- 受信した UDP ペイロードの概要を標準出力へ表示し、全体を hexstring としてテキストログファイルへ記録する。
- 将来、特定タイプの UDP ペイロードを判別して整形表示する機能を追加可能な構造とする。

## 3. プログラム構成

| プログラム | 実行ファイル名 | 常駐 | 役割 |
| --- | --- | --- | --- |
| UDP 通信サーバ | `udp_server` | する | 外部マシンとの UDP 送受信、受信ペイロードの表示、および送信指示の受信 |
| UDP 送信指示クライアント | `udp_sender` | しない | 指定ファイルを読み取り、各行のペイロードをバイナリ化してサーバへ送信指示 |

## 4. UDP 通信サーバ

### 4.1 動作

- 起動後、終了指示を受けるまで常駐する。
- 外部マシンからの UDP パケットを非同期に受信する。
- 受信した UDP パケットの受信時刻、サイズおよび通し番号を標準出力へ表示し、全ペイロードを hexstring でテキストログファイルへ記録する。
- プロセス間通信（IPC）を通じて UDP 送信指示クライアントから送信要求を受け付ける。
- 受け付けた送信要求に従い、外部の宛先へ UDP パケットを非同期に送信する。

### 4.1.1 終了

- 初版における終了操作は、対話コンソールでの `Ctrl+C` とする。
- Windows、macOS、および Ubuntu Linux の各 OS で `Ctrl+C` による割り込み（`SIGINT`）を受け付ける。
- 割り込みを受けたサーバは、新規の UDP 受信および IPC 受け付けを停止し、使用中のソケットおよび IPC リソースを閉じて正常終了する。
- サービス化、バックグラウンド起動時の終了方法、または OS 固有の終了操作は初版の対象外とする。

### 4.1.2 設定

- UDP 通信サーバは、JSON 設定ファイルのパスを必須のコマンドライン引数として受け取る。
- 設定ファイル名および配置場所は固定しない。異なる設定ファイルを指定することで、同一ホスト上で複数の UDP 通信サーバを起動し、相互に組み合わせ試験できるようにする。
- JSON 設定ファイルには、UDP 送信先の IPv4 アドレスおよびポート、ならびに UDP 受信用待受 IPv4 アドレスおよびポートを記載する。
- JSON 設定ファイルには、IPC 用 TCP サーバの待受ポートも記載する。
- JSON 設定ファイルの読み込みには `nlohmann/json` を使用する。
- 設定は単純なキーと値の組み合わせとし、次のキーを必須とする。

```json
{
  "listen_address": "0.0.0.0",
  "listen_port": 5000,
  "destination_address": "192.0.2.10",
  "destination_port": 5001,
  "ipc_port": 5002
}
```

- `listen_address`: UDP の待受に使用する IPv4 アドレス。
- `listen_port`: UDP の待受に使用するポート番号。
- `destination_address`: IPC から指示された UDP ペイロードの送信先 IPv4 アドレス。
- `destination_port`: IPC から指示された UDP ペイロードの送信先ポート番号。
- `ipc_port`: IPC 用 TCP サーバの待受ポート番号。TCP サーバは IPv4 ループバックアドレス `127.0.0.1` だけに bind する。
- 次のキーは任意とする。

```json
{
  "packet_log_path": "logs/received.log",
  "packet_log_queue_limit_bytes": 8388608
}
```

- `packet_log_path`: 受信パケットの全hexダンプを記録するテキストログファイルのパス。相対パスは設定JSONファイルが置かれたディレクトリから解決する。指定したパスの既存ファイルには追記する。キーがない場合は、設定JSONファイルと同じディレクトリに、起動時刻を用いた `udp_packets_YYYYMMDD-HHMMSS-mmm.log` 形式の新規ファイルを生成する。同名ファイルが存在する場合は、重複しない連番をファイル名へ付加する。自動生成・指定を問わず、ログファイルを開けない場合はサーバを起動せず、エラーログを出力して異常終了する。
- `packet_log_queue_limit_bytes`: 出力待ちキューに保持するUDPペイロードの合計バイト数の上限。正の整数で指定し、未指定時は `8388608`（8 MiB）とする。
- 設定ファイルのコマンドライン引数が欠落している場合、ファイルを読み込めない場合、JSON 構文エラー、必須キーの欠落、または設定値が不正な場合、サーバは `spdlog` の `error` レベルでエラー内容を標準エラー出力へ 1 行で表示して異常終了する。

### 4.1.3 IPC サーバ

- IPC 方式は TCP ループバック通信とする。
- サーバは `127.0.0.1:<ipc_port>` で TCP 接続を非同期に受け付ける。
- TCP の待受をループバックアドレスに限定し、外部ホストからの IPC 接続を受け付けない。
- IPC クライアントから受け取った送信要求に従い、設定済みの UDP 送信先へ UDP データグラムを非同期に送信する。
- サーバは UDP 送信処理の完了後、成功または失敗を IPC クライアントへ応答する。

### 4.2 受信ペイロードの表示と記録

- UDP受信が成功した時点で、受信時刻をローカル時刻・ミリ秒精度で採取する。ログ出力スレッドで書き込んだ時刻ではなく、この受信時刻を画面およびファイルの各パケット記録に使用する。
- サーバプロセスの起動ごとに、正常に受信したUDPパケットへ `1` から始まる通し番号を付与する。ログキューからの破棄が発生しても、通し番号は連続して進める。
- 画面には各UDPパケットを `spdlog` の `info` レベルで標準出力へ1行で表示する。表示形式は `Received(<バイト数>): <通し番号>` とし、ペイロードのhexダンプは表示しない。
- 例: 通し番号123の4バイトのUDPパケットを受信した場合、画面出力は `[2026-08-18 12:34:56.789] [info] Received(4): 123` とする。
- ファイルには各UDPパケットを1行で記録する。画面と同じ受信時刻、ログレベル、サイズおよび通し番号の後に `: ` を付け、区切りなし・大文字のhexstringを続ける。例: `[2026-08-18 12:34:56.789] [info] Received(4): 123: DEADBEEF`。
- ログファイルのローテーションは行わない。1パケットごとのflushは要求せず、通常のバッファリングを使用する。正常終了時には、保留中のログをファイルへflushしてから終了する。
- エラーは `spdlog` の `error` レベルを用いて標準エラー出力へ1行ごとに出力し、タイムスタンプおよびログレベルの後に `Error: <エラー内容>` を出力する。

### 4.2.1 ログ出力

- ログライブラリにはヘッダオンリー版の `spdlog` を使用する。
- 初期化時に `spdlog::set_pattern("[%Y-%m-%d %H:%M:%S.%e] [%l] %v")` を設定し、すべてのログ行の先頭にミリ秒精度のローカル時刻とログレベルを出力する。パケット受信記録だけは、受信完了時に採取した時刻を使用する。
- 正常な UDP 受信概要は `info` レベルで標準出力へ出力し、全hexダンプはログファイルへ出力する。
- 検出したエラーは `error` レベルで標準エラー出力へ出力する。
- 出力待ちキューの破棄発生は `warn` レベルで標準エラー出力およびログファイルへ1行で出力する。
- 初版で使用するログレベルは `info`、`warn` および `error` とする。`debug` と `trace` は将来拡張用として予約する。

### 4.2.2 非同期ログキュー

- UDP受信を、hex文字列への変換、画面出力またはファイル書き込みによって待たせない。受信スレッドは受信時刻、通し番号およびペイロードを出力待ちキューへ渡し、出力専用スレッドがhex変換と各出力先への書き込みを行う。
- 出力待ちキューの容量は `packet_log_queue_limit_bytes` に従う。キューへの追加で上限を超えそうな場合、受信スレッドは待機・ブロックしない。
- 上限超過時は、キューに保留中の画面表示およびファイル記録を一括で破棄する。破棄されたパケット記録の件数を集計し、出力専用スレッドが処理を再開した時点で `Warning: packet log queue overflow; discarded <件数> packet logs` の形式で `warn` ログを出力する。
- キューをクリアした後も、以降に受信したパケットの受付および記録を継続する。ログキューの破棄はUDPパケットを受信できなかったことを意味しない。

### 4.3 将来拡張

- ペイロード種別を判別する仕組みを追加できるようにする。
- 対応するペイロード種別は、hexstring ダンプではなく意味を持つ項目として整形表示できるようにする。
- 未対応または判別不能なペイロードは hexstring ダンプを維持する。

## 5. UDP 送信指示クライアント

### 5.1 起動と終了

- コマンドライン引数で、サーバと共通の JSON 設定ファイルのパス、および送信する UDP ペイロード情報を記載したファイルのパスを受け取る。
- 引数の順序は、`<設定JSONファイル> <UDPペイロードファイル>` とする。
- クライアントは設定ファイルから `ipc_port` を読み込み、`127.0.0.1:<ipc_port>` の IPC サーバへ TCP 接続する。
- クライアント側の TCP ローカルポートは OS が一時ポートを自動割り当てするため、設定しない。
- ファイルの全行について送信指示を完了した後、終了する。
- 新たな送信が必要な場合は、クライアントを改めて起動する運用とする。

### 5.2 入力ファイル

- テキストファイルとする。
- 1 行を 1 UDP パケットに対応させる。
- 各行にはバイナリ値そのものではなく、ASCII 文字で表現した hexstring を記載する。
- クライアントは各行の hexstring をバイナリの UDP ペイロードへ変換する。
- 空行は無視し、UDP パケットを送信せずに次の行を処理する。
- 行区切り以外の空白文字は基本的に無視する。したがって、hexstring 内には空白文字を含められる。特殊行では、コマンド名と引数を空白文字で区切る。
- hexstring の英字は大文字・小文字を区別せず、混在も許容する。
- 行頭が `#` の行はコメント行とし、UDP パケットを送信せずに次の行を処理する。
- 行頭が `/` の行は特殊行とする。`/` の直後にコマンド名を記載し、コマンド名と引数は1文字以上の空白文字で区切る。コマンド名は大文字・小文字を区別する。
- 初版で定義する特殊コマンドは `Wait` のみとする。`/Wait <待機時間>` は、指定時間だけ sleep した後に次の行を処理する待機指示である。待機時間は10進整数でミリ秒単位で記載する。
- 待機指示行の例: `/Wait 250` および `/Wait    250` は、ともに250ミリ秒待機することを表す。
- クライアント実装では、特殊行のプレフィクス `/` と待機コマンド名 `Wait` を、それぞれ名前付き定数として定義する。将来のコマンド名・プレフィクス変更時は、この定義値だけを変更して対応できる構成とする。
- 待機時間は 0 から 1,800,000 ミリ秒（30 分）までとする。
- 未定義の特殊コマンド、不正な hexstring、待機時間の書式不正、または待機時間の上限超過は入力ファイルの形式エラーとする。クライアントは `spdlog` の `error` レベルでエラー内容を標準エラー出力へ 1 行で表示して異常終了する。

### 5.3 送信指示

- クライアントは、変換済みのバイナリ UDP ペイロード情報を、確立済みの IPC 用 TCP 接続でサーバへ送る。
- クライアントは 1 回の起動につき 1 本の TCP 接続を使用し、全行の処理後に接続を切断する。
- 1 件の送信要求は、4 バイトの符号なしビッグエンディアン整数で表したペイロード長と、その直後に続くバイナリ UDP ペイロードで構成する。
- ペイロード長は 0 から 32,768 バイトまでとする。
- クライアントは各送信要求の後に、サーバからの UDP 送信完了応答を待機してから次の行を処理する。
- UDP 送信完了応答は 1 バイトの結果コードとする。`0` は成功、それ以外は失敗を表す。
- サーバへの TCP 接続に失敗した場合、または失敗結果コードを受信した場合、クライアントは `spdlog` の `error` レベルでエラーを表示して異常終了する。
- UDP ペイロードファイルを開けない場合、またはファイル内の hexstring・特殊コマンド・待機時間指定が不正である場合、クライアントは `spdlog` の `error` レベルでエラー内容を標準エラー出力へ 1 行で表示して異常終了する。

## 6. UDP ペイロードと長さ

- UDP ペイロードの長さは可変とする。
- 1 UDP パケットの UDP ペイロード長の上限は 32,768 バイトとする。
- 大きな UDP データグラムは、OS とネットワークの IP フラグメンテーションおよび受信側 IP スタックによる再構成を利用して配送できる構成を想定する。
- アプリケーション独自の分割・再構成は、初版の対象外とする。
- UDP 送信・受信時に OS またはソケット API が検出したエラーは、エラーログへ出力する。これには、経路 MTU 等に起因するローカルな送信エラーを含む。
- ネットワーク上での IP フラグメント喪失による受信側の再構成失敗は、送信側からは通常検出できない。この種の失敗を送信側でエラーログに出力することは初版の対象外とする。

## 7. 非同期処理

- UDP 通信サーバは Asio の非同期 API を用いて UDP 受信および UDP 送信を行う。
- UDP 通信サーバは Asio の非同期 API を用いて、IPC 用 TCP 接続の accept、要求の read、および応答の write を行う。

## 8. クロスプラットフォーム要件

- 対応 OS は Windows、macOS、Ubuntu Linux とする。
- IP 通信は IPv4 のみ対応する。
- 可能な限り OS 固有コードを分離し、共通の通信・ペイロード処理ロジックを共有する。
- IPC は上記 3 OS で利用可能な方式を採用する必要がある。

## 9. 制約・対象外

- 初版では、同一サーバへ接続する送信指示クライアントの複数同時起動を想定しない。この場合の動作は未定義とする。
- IP フラグメンテーションでネットワーク上において失われた UDP データグラムを、アプリケーションで検出または再送する機能は対象外とする。
- サービス化、バックグラウンド起動時の終了方法、および OS 固有の終了操作は対象外とする。

## 10. ビルド環境

### 10.1 共通

- ビルドシステムは CMake 3.20 以降を使用する。
- CMake のビルドジェネレーターは Ninja を使用する。
- C++ 言語標準は C++20 とする。
- 依存ライブラリはヘッダオンリーライブラリのみを想定し、ソースコードまたは配布物とともにダウンロードして利用する。ヘッダオンリー以外の依存関係が必要になった場合は、別途方針を決定する。
- OS 固有の設定は CMake 上で分離し、共通のソースコードから各 OS 向けの実行ファイルを生成する。

### 10.2 Windows

- MinGW-w64 系のツールキットを使用する。
- 初版では w64devkit を利用可能な開発環境として想定する。
- CMake、Ninja、および w64devkit に含まれる C++ コンパイラを利用してビルドする。

### 10.3 macOS

- Xcode Command Line Tools、または Xcode に含まれる Apple Clang を C++ コンパイラとして使用する。
- macOS の `gcc` コマンドは通常 GNU GCC ではなく Apple Clang の互換コマンド名である。本プロジェクトでは `clang` または `clang++` を明示して使用することを推奨する。
- Homebrew を用いて CMake および Ninja を導入し、Ninja ジェネレーターでビルドする。

### 10.4 Ubuntu Linux

- GCC または Clang のいずれかを C++ コンパイラとして使用する。
- CMake および Ninja（パッケージ名は通常 `ninja-build`）を導入し、Ninja ジェネレーターでビルドする。
