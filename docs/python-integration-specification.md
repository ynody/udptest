# Python 版統合 UDP 通信アプリ仕様書

## 1. 文書の目的と位置付け

本書は、既存の C++ UDP 通信プログラムと並行して提供する Python 互換版の動作、入出力、ログ、および互換性要件を定める。実装は `python/udpcomapp.py`、uv 環境と依存定義は `python/` 以下に置く。本書は引き続き動作要件と C++ 版との差異の基準となる。

既存 C++ ソースで確認できる内容を互換要件として扱い、C++ のソースと既存文書の記述が異なる箇所、または C++ から判断できない箇所は「仕様判断・未確定事項」に明示する。

## 2. 目的と範囲

- 送信と受信を一つの Python スクリプトおよび一つの実行プロセスで扱う。
- 起動後は対話型テキスト UI（TUI）のコマンドプロンプトを表示し、受信を継続しながら、利用者が `send <file-path>` コマンドで指定したペイロードファイルを FIFO 順に処理して UDP 送信する。
- 送信データグラムのペイロードは既存 C++ 版と同じ最大 32,768 バイトとする。
- 既存の設定 JSON とペイロードファイル構文を可能な限り維持する。
- 受信ペイロードの全体を、既存 C++ 版に近い行形式でパケットログへ記録する。
- 送信、エラー、起動・終了などのイベントは別のイベントログへ記録する。イベントログには UDP ペイロードの内容を含めず、送信サイズと発生時刻を記録する。
- 対象 OS は既存仕様を引き継ぎ、Windows、macOS、Ubuntu Linux とする。ネットワークは IPv4 のみを対象とする。
- この版では、サービス化、バックグラウンド運転、再送、受信確認応答、ペイロード種別ごとのデコードを扱わない。

## 3. 実行環境と依存関係

- Python は uv 管理の Python 3.14 系を使用する。Python 3.13 を既定とする既存 `AGENTS.md` の記述より、本タスクで指定された 3.14 を優先する。
- プロジェクトルートからの起動例は `uv run --project python --python 3.14 python python/udpcomapp.py <settings-json>` とする。設定 JSON のパスは必須とする。
- TUI には Textual を使用する。UDP ソケット、JSON の読み込み、時刻、スレッドまたは非同期処理、ログ出力には Python 標準ライブラリを使用する。
- Python 版は C++ 版の Asio、nlohmann/json、spdlog を依存関係として使用せず、CMake によるビルドも必要としない。既存 C++ ソースおよびそのビルド設定は変更しない。
- Textual 8.2.8 は利用者が既存プロジェクトと同じ TUI ライブラリとして選択し、`python/pyproject.toml` と `python/uv.lock` で固定する。Python 3.14.4 の macOS 環境で UI Pilot と loopback 統合テストを実施した。Windows と Ubuntu Linux の端末入力・再描画は未確認である。
- 他の第三者ライブラリや実行時フレームワークを追加する場合は、名前、採用理由、代替案、トレードオフを先に提示して利用者の承認を得る。選定済み依存は `libraries.md` に記録する。
- `uv` は Python 3.14 環境と固定済み Textual 依存を管理する。

### 3.1 Python 版の配置

- Python 版として新規作成する実行コード、uv の環境・依存定義、ロックファイル、テスト、Python 版専用の運用文書や配布用ファイルは、すべてプロジェクトルートの `python/` 以下に置く。既存の C++ 用 `src/`、`CMakeLists.txt`、`third_party/` には Python 版のファイルを追加しない。
- 実行コードは送受信と TUI を担当する単一スクリプト `python/udpcomapp.py` とする。実装時の配置例は `python/pyproject.toml`、`python/uv.lock`、`python/.python-version`、`python/tests/` とし、必要なファイルだけを作る。
- 本仕様書は既存の文書配置に合わせて `docs/` に置く。運転時のログ保存先は 4.2 節の設定パス規則に従い、ソースコードの配置先とは独立する。

### 3.2 TUI ライブラリの選定

Textual を選定する理由は、既存の利用者プロジェクトと TUI ライブラリを揃えられ、コマンド入力欄、状態表示、イベント表示を一つの対話 UI として構成できるためである。受信・送信のバックグラウンド更新とコマンド入力を同時に扱い、端末へ直接出力して入力行を崩す問題を避けやすい。

- `prompt_toolkit` は入力欄とプロンプト制御に向くが、状態・イベントパネルを別途組み立てる必要がある。
- Rich と標準ライブラリの組み合わせでも画面表示は作れるが、入力・バックグラウンド更新の調整をアプリ側で多く担う。
- 標準ライブラリのみなら外部依存を避けられる一方、端末画面の再描画と入力維持を独自に実装する必要があり、本アプリの並行受信・送信表示には不利である。
- Textual は Python 外部依存とパッケージ容量を増やす。採用版 8.2.8 は Python 3.14.4 の macOS 環境で起動・入力・再描画を確認した。Windows と Ubuntu Linux の端末動作は未確認である。
- Textual の固定版は 8.2.8 とし、uv の依存定義・ロックで管理する。

## 4. 設定 JSON

### 4.1 キー

既存 C++ 版の設定 JSON は変更せず、そのまま Python 版の起動引数に指定できる。既存の必須キーは同じ意味で読み取り、`ipc_port` は受け入れるが Python 版では使用しない。Python 版で追加するキーはすべて任意とし、既存ファイルでは既定値を適用する。

以下のキーを扱う。

| キー | 必須 | 意味・検証 |
| --- | --- | --- |
| `listen_address` | はい | UDP 待受 IPv4 アドレス。例: `127.0.0.1`、`0.0.0.0` |
| `listen_port` | はい | UDP 待受ポート。整数 1～65535 |
| `destination_address` | はい | UDP 送信先 IPv4 アドレス |
| `destination_port` | はい | UDP 送信先ポート。整数 1～65535 |
| `packet_log_path` | いいえ | 受信パケットログのパス |
| `packet_log_queue_limit_bytes` | いいえ | 受信ログ待ちキューのペイロード合計上限。正の整数。既定値は 8 MiB（8,388,608 バイト） |
| `packet_log_queue_limit_packets` | いいえ | 受信ログ待ちキューのレコード数上限。正の整数。既定値は 4,096 件。0 バイトデータグラムの集中でキューのメモリ使用量が増え続けないようにする |
| `receive_socket_buffer_bytes` | いいえ | `SO_RCVBUF` に要求する受信ソケットバッファサイズ。正の整数。既定値は 4 MiB（4,194,304 バイト）。OS が設定値を制限または調整する場合がある |
| `event_log_path` | いいえ | 送信・エラー・運転イベントのログパス。Python 版で追加するキー |
| `ipc_port` | いいえ | C++ 設定ファイルとの共用のため受け入れるが、Python 版では使用しない |

設定例:

```json
{
  "listen_address": "127.0.0.1",
  "listen_port": 5000,
  "destination_address": "127.0.0.1",
  "destination_port": 5001,
  "ipc_port": 6000,
  "packet_log_path": "logs/received.log",
  "event_log_path": "logs/events.log",
  "packet_log_queue_limit_bytes": 8388608,
  "packet_log_queue_limit_packets": 4096,
  "receive_socket_buffer_bytes": 4194304
}
```

### 4.2 パスと起動検証

- 相対ログパスは設定 JSON が置かれたディレクトリを基準に解決する。
- `packet_log_path` を省略した場合は、設定 JSON と同じディレクトリに `udp_packets_YYYYMMDD-HHMMSS-mmm.log` 形式の一意な新規ファイルを作る。衝突した場合は連番を付ける。
- `event_log_path` を省略した場合も同じディレクトリに `udp_events_YYYYMMDD-HHMMSS-mmm.log` 形式の一意な新規ファイルを作る。
- 二つのログパスが同じファイルを指す場合は起動エラーとする。ログの親ディレクトリは事前に存在していなければならない。
- 指定されたログファイルを開けない場合は、UDP ソケットを bind する前に起動を中止する。
- 設定ファイルの読み込み、JSON 構文、必須キー、型、IPv4 アドレス、ポート番号、ログキュー上限、`receive_socket_buffer_bytes` のいずれかに問題があれば、ペイロードを表示せず、標準エラー出力へタイムスタンプ付きのエラーを 1 行出して異常終了する。
- JSON の真偽値は整数ポートや整数キュー上限として扱わない。未定義キーは無視する。`ipc_port` は値の有効性にかかわらず通信には使用しない。
- `packet_log_queue_limit_bytes` と `packet_log_queue_limit_packets` はどちらも正の整数とし、キューは両方の上限を同時に満たす。`receive_socket_buffer_bytes` は正の整数とする。

## 5. ネットワーク動作

- 起動時に一つの IPv4 UDP ソケットを `listen_address:listen_port` へ bind する。同じソケットを受信と送信に使用し、設定済みの `destination_address:destination_port` へ直接 `sendto` する。
- 起動後は UDP 受信を継続し、TUI から送信操作を受け付ける。送受信は同じプロセスで並行して進行する。
- C++ 版のループバック TCP IPC は使わない。Python 版はローカル TCP リスナーを起動せず、C++ `udp_sender` から送信指示を受け付けない。C++ `udp_sender` は従来どおり、TCP IPC を提供する C++ `udp_server` に接続する。
- UDP の送信成功は、ローカル OS のソケットがデータグラムを受け付けたことを示すだけであり、宛先への到達や相手の受信を保証しない。アプリケーション層の ACK、再送、順序保証は行わない。
- 送信ペイロードの上限は 32,768 バイト。上限超過は該当行の送信前に検出し、エラーとして扱う。
- 送信元ポートは bind した `listen_port` である。別プロセスが同じ待受アドレス・ポートを使用中なら起動に失敗する。

### 5.1 受信・送信・UI・ログの並行構成

- Textual のメイン asyncio ループが UI とコマンド受付を担当する。UDP 受信は専用の受信スレッド、送信ファイル処理は独立した単一の送信ワーカースレッドが担当し、ログファイルへの書き込みはログ専用スレッドだけが行う。受信スレッドは端末表示やログファイル書き込みをしない。
- 受信ソケットには専用の受信スレッドだけが `recvfrom(65535)` を実行する。IPv4 UDP の最大ペイロード 65,507 バイトを収容し、データグラムを途中で切らずに取得する。送信ワーカーは同じ IPv4 UDP ソケットから `sendto` する。
- 受信スレッドは、受信完了時刻の採取、通し番号と受信件数の更新、受信ログ用の不変レコード（時刻・番号・ペイロード）の容量待ちをしない enqueue、共有カウンターの更新、UI 更新要求の coalesced 通知だけを行う。hex 変換、文字列整形、イベントログ書き込み、Textual widget の更新は行わない。
- 受信ログ用の有界キューは短いロック区間で長さと上限を確認して enqueue する。満杯時に受信スレッドを待たせない。詳細な満杯時動作とカウンターは 7.2 節に定める。
- パケットログ writer は受信ログキューを FIFO で取り出し、hex 変換とパケットログ書き込みを行う。イベントログも受信スレッドや送信ワーカーから分離したイベントログ writer が書き込む。二つの writer はファイルを共有しない。
- Textual へのバックグラウンド通知は、最新受信概要・カウンターと容量 100 件の表示通知メールボックスで行う。受信・送信 worker は通知を集約してから `loop.call_soon_threadsafe` でメインループへスレッドセーフに通知する。同時に未処理の refresh callback は最大 1 件、画面更新は最大 10 回/秒とする。メインループ上の callback だけが Textual widget を更新する。複数の受信通知は最新概要へ集約し、表示通知が満杯なら表示用の古い項目を落として集約数を増やす。これはログキューには影響せず、受信件数やログ破棄数のカウンターは保持する。
- 受信ループは短い待受 timeout（最大 250 ms）を使い、終了要求後も遅くとも次の timeout で停止できるようにする。タイムアウトはエラーや受信件数に数えない。終了時は受信スレッドを止めてからログキューを drain する。
- `SO_RCVBUF` の要求値は bind 前に `setsockopt` で設定し、その後 `getsockopt` で OS が報告する有効値を取得する。要求値・有効値を起動イベントと TUI 状態に表示する。設定に失敗した場合はエラー内容と OS 既定値の読み取り結果を記録し、ソケットが利用可能なら OS 既定値で起動を続ける。有効値を読み取れない場合は「取得不可」と表示する。
- `SO_RCVBUF` は OS が保証する受信容量ではなく、実効値が要求値と一致する保証もない。Linux は会計上の理由で `getsockopt` 値を要求値の約 2 倍として報告することがあり、カーネル設定による上限もある。Windows と macOS もシステム上限やソケット実装により要求を丸めたり制限したりする。表示値は OS が返した値であり、実際に受信できるデータグラム数を保証しない。

## 6. TUI コマンドと送信ファイルの操作

### 6.1 Textual 画面とコマンドプロンプト

TUI は Textual で構成し、Windows、macOS、Ubuntu の標準端末で動作するものとする。画面は上部ヘッダー、状態パネル、直近イベント一覧、下部コマンド入力欄の構成とする。

- 上部ヘッダーは UDP 待受アドレス・ポート、送信先アドレス・ポート、解決済みのパケットログとイベントログのパスを表示する。パスが横幅を超える場合は折り返す。
- 状態パネルは受信の稼働状態、受信総数、パケットログ記録済み数、アプリのログキュー破棄数、キュー深度、OS UDP 受信破棄数または取得不可、`SO_RCVBUF` の要求値・有効値または設定エラー、送信ワーカー状態、処理中または最後に失敗したファイルと行番号、保留中ファイル数、完了・失敗数を表示する。
- 直近イベント一覧は時刻付きの受信概要、送信サイズ・宛先、状態変化、警告、エラーをペイロードなしで表示する。受信行はサイズと通し番号を含め、集約がある場合はその件数も示す。これはログファイルの代わりではなく、アプリ実行中の画面表示である。
- 直近イベント一覧は全画面幅でスクロール可能とし、最大 100 行だけをメモリ上の画面履歴として保持する。101 件目以降を追加するたびに最も古い表示行を取り除く。表示から外れた行も追記型のイベントログ／パケットログの各方針に従って保存する。
- 下部コマンド入力欄は常に表示し、利用者は 1 行ずつ入力する。UDP 受信中、送信中、`/Wait` 待機中も入力でき、入力中の文字列はイベント更新や画面再描画で消去・上書きしない。
- 画面幅が 100 文字以上の場合、状態とイベント一覧を横並びにする。100 文字未満の場合は縦に並べる。端末リサイズ時は内容を再配置し、コマンド入力欄を利用可能な状態に保つ。
- バックグラウンドの受信処理・送信ワーカー・ログ writer は端末へ直接 `print` したり、Textual 管理外から画面を書き換えたりしない。UI の状態更新・イベント表示は容量制限と集約を持つスレッドセーフな通知を介し、Textual のメイン asyncio ループ経由で行う。
- 非同期受信・送信イベントの更新で入力欄を消去、上書き、分断しない。利用者が入力中の文字列はそのまま保持し、画面の再描画だけを行う。
- 受信したペイロードの内容を画面上のいずれの領域にも表示しない。画面上の受信表示は時刻と `Received(<バイト数>): <通し番号>` の概要に限る。

画面表示例（パスや数値は例示。イベント一覧は新しい項目を下へ追加し、スクロールして確認できる）:

```text
UDP Communication                                      RUNNING
Listen: 127.0.0.1:5000      Destination: 192.0.2.10:5001
Packet log: /work/logs/received.log
Event log:  /work/logs/events.log
RX: active | Received: 18
TX: sending examples/packets-a.txt:12 | Queued: 2 | Completed: 3 | Failed: 1

Recent events (up to 100)
[2026-11-04 10:12:01.234] RX Received(4): 18
[2026-11-04 10:12:02.345] TX Transmitted(4): 192.0.2.10:5001
[2026-11-04 10:12:03.456] ERROR line 12: invalid hexadecimal character

> send ./examples/packets next.txt
```

コマンド入力 UI は UDP 受信および送信ワーカーを待たせず、入力を受け付ける。

最低限、次の小文字コマンドを提供する。

| コマンド | 動作 |
| --- | --- |
| `send <file-path>` | 指定ファイルを送信キューの末尾へ登録する。登録後は単一の送信ワーカーが直ちに FIFO 順で処理し、既に処理中でも登録できる |
| `status` | 受信状態、送信中またはエラー一時停止中の状態、ファイルと行番号、キュー内のファイル数、完了・失敗数を表示する |
| `help` | 使用可能なコマンドとパスの指定方法を表示する |
| `resume` | ファイル処理エラー後に一時停止した送信キューを再開し、次のファイルから FIFO 順に処理する |
| `quit` | TUI とプログラム全体を終了する。新規コマンドと送受信を停止し、保留中の受信ログを出力してログを閉じる |

コマンド名は小文字で、完全一致とする。空行は無視する。未知コマンドや引数不足はイベントログに記録し、簡潔なエラーと `help` の案内を TUI に表示してプロンプトへ戻る。

### 6.2 `send` コマンドのパス構文

- コマンドの最初の空白までをコマンド名とし、`send` の後の残り全体をファイルパスとして扱う。パスをシェル風に単語分割しないため、`send ./test packets/first.txt` は空白を含む一つのパスである。
- パス両端の空白は取り除く。先頭または末尾の空白をパス名に含めたい場合は、パス全体を同種の一重引用符または二重引用符で囲む。囲み内の文字はそのままパスとして扱い、バックスラッシュによるエスケープは行わない。先頭に引用符があるのに対応する末尾引用符がない場合は構文エラーとして受け付けない。
- 環境変数展開、チルダ展開、glob 展開、シェル実行は行わない。相対パスはアプリケーションの起動時の現在ディレクトリを基準に解決する。
- `send` を受け付けた時点で、指定先が通常ファイルとして存在し読み取り可能かを確認する。条件を満たさないパスはキューに追加せず、イベントログにエラーを記録して TUI に戻る。
- 受け付けたパスは送信キューの末尾に追加する。コマンド受付と送信処理は独立するため、送信中でも何度でも `send` を実行でき、後から受け付けたファイルは既存キューの後に送る。エラーでキューが一時停止している間も新しいファイルを追加できるが、`resume` までは送信しない。

### 6.3 送信ファイルの読み方

一つのファイルを先頭から末尾まで 1 行ずつ読み、行ごとに解析・送信または待機を行ってから次の行へ進む。ファイル全体を UDP ペイロード一覧としてメモリに読み込まない。送信ワーカーは一つだけとし、ファイル間でも同時送信を行わず、FIFO 順を維持する。

### 6.4 送信行の構文

既存 C++ `udp_sender` と同じ規則を使う。

- 1 行を 1 データグラムまたは 1 待機指示に対応させる。
- 空行および空白文字だけの行は無視し、送信しない。
- 行の先頭文字が `#` のとき、その行全体をコメントとして無視する。先頭空白の後に `#` がある行はコメントではない。
- 行の先頭文字が `/` のとき、特殊コマンドとして解析する。コマンド名は大文字・小文字を区別し、初版で有効なのは `/Wait <ミリ秒>` のみ。
- `/Wait` の待機値は 10 進整数で 0～1,800,000 ミリ秒とする。コマンド名と引数の間は空白文字で区切る。C++ の実装に合わせ、引数内の空白文字は数値の解釈前に無視する。
- それ以外の行は 16 進数のペイロードとして扱う。`0`～`9`、`A`～`F`、`a`～`f` を受け入れ、大文字小文字を区別しない。行内の空白文字はすべて無視する。
- 有効なペイロード行は空白を除いた 16 進桁数が偶数でなければならない。不正な文字、奇数桁、32,768 バイト超過はエラーとする。
- 既存構文では空行は無視されるため、ファイルから 0 バイトの UDP データグラムは送信できない。空データグラム送信の専用 UI 操作は本仕様に含めない。
- `/` や `#` の前に空白を置いた行は特殊行・コメント行にならず、ペイロードとして検証される。

### 6.5 逐次送信とエラー

- 各データグラムの送信完了後に次のデータ行へ進む。`/Wait` は指定時間待ってから次行の処理を行う。
- TUI は現在のファイル、行番号、送信済みデータグラム数、成功した送信サイズを表示してよいが、ペイロードの文字列や hex を表示してはならない。送信ワーカーが処理中でも、コマンドプロンプトは次の入力を受け付ける。
- `send` コマンドで既に存在確認したファイルが、処理開始までに削除または読み取り不可となった場合、あるいは処理中に読み込みエラー・行構文エラー・ソケット送信エラーが発生した場合は、イベントログに記録して現在のファイルだけを失敗終了する。構文不正・送信失敗の該当行は送信しない。
- ストリーム処理のため、エラー行より前に送信済みのデータグラムは取り消せない。失敗したファイルの残りの行は送らない。エラー後の後続ファイルは自動処理せずキューに残し、送信ワーカーを一時停止する。利用者が `resume` を入力した場合に限り、失敗したファイルを再試行せず、次のファイルから FIFO 順に処理を再開する。
- エラー表示にはファイル名と 1 始まりの行番号を含める。エラー行の内容や、その行から得られるペイロードはログに記録しない。
- `status` は受信が稼働中か、送信ワーカーが稼働中かエラーで一時停止中か、現在または最後に失敗したファイルと処理行、未処理のキュー件数、完了件数、失敗件数を表示する。ペイロードの内容は表示しない。
- `resume` はエラーで一時停止したキューがある場合にそれを再開する。再開対象がなければ「再開するキューはない」と表示し、イベントログにはエラーとして記録しない。
- `quit` は新しいコマンドの受け付けを止め、未処理キュー内のファイルを破棄し、現在のファイルの処理を停止する。進行中のローカル UDP 送信操作があればその完了後に停止し、待機中の `/Wait` は直ちに中断する。ネットワーク上の受信応答を待たず、未処理ファイルを drain しないため、長いキューや待機時間で終了が遅延しない。破棄したキュー件数と停止対象ファイルをイベントログに記録する。既に送信されたデータグラムは取り消せない。

## 7. UDP 受信とパケットログ

### 7.1 受信記録

- 受信成功時に採取したローカル時刻を、TUI およびパケットログの記録時刻として使う。ログスレッドが後で出力した時刻に置き換えない。
- 通し番号はプロセス起動ごとに 1 から開始し、正常に受信したデータグラムごとに 1 増やす。ログキューによる記録破棄があっても番号を戻さない。
- 受信総数はログキューへの enqueue 成否とは独立して増やす。キューへ記録できなかったパケットも受信総数と通し番号に含める。
- Textual の直近イベント一覧には、ペイロードを含めず受信概要を表示する。受信量が多い場合は最大 10 回/秒の更新に集約し、各表示行は最新の `Received(<バイト数>): <通し番号>` と集約件数を示す。RX 状態パネルの受信総数は集約による間引きの影響を受けない。受信・送信ワーカーから標準出力や画面へ直接書き込まない。
- パケットログは次の形式とする。時刻、ログレベル、サイズ、通し番号は TUI の受信概要と一致させる。

```text
[2026-08-18 12:34:56.789] [info] Received(4): 123: DEADBEEF
```

- hex は区切りなし、大文字、1 バイトあたり 2 桁とする。0 バイトの受信データグラムは `Received(0): <番号>: ` と記録する。
- パケットログのローテーションは行わない。終了時には保留中の受信記録を出力し、ファイルを flush する。
- パケットログには正常に受信した UDP データグラムの記録だけを含める。警告、エラー、起動・終了情報、送信情報はこのファイルへ書かない。

### 7.2 受信サイズとログキュー

- 送信上限は既存仕様に合わせ 32,768 バイトとする。受信スレッドは `recvfrom(65535)` で受け取り、IPv4 UDP の最大ペイロード 65,507 バイトを全量収容する。受信データを途中で切り詰めた hex を完全なパケットとして記録しない。
- 32,768 バイトを超える受信データグラムも、受信した実サイズと全ペイロードをパケットログに記録する。上限超過の警告はイベントログにだけ記録する。これは送信上限とは別の受信時扱いであり、既存 C++ の 32,768 バイト受信バッファより受信ログを完全に保つための仕様判断である。
- 受信スレッドは受信時刻・通し番号・ペイロード bytes を一つの不変レコードにして、パケットログ writer の有界 FIFO キューへパケットごとに一回 enqueue する。hex 変換やファイル I/O を行わない。enqueue 時のロック区間は上限確認、O(1) の追加、キュー深度・バイト数更新に限る。
- `packet_log_queue_limit_bytes` はキュー内ペイロード bytes の合計上限（既定 8 MiB）、`packet_log_queue_limit_packets` はレコード数上限（既定 4,096 件）であり、両上限を同時に適用する。bytes 上限にはペイロードと固定サイズのレコード管理分を含めないが、件数上限により 0 バイトなど小さいレコードが大量に滞留してもレコード数が際限なく増えない。
- キューが満杯、または今回のレコード単独で bytes 上限を超える場合は、その時点で到着した今回の記録だけを破棄し、既にキューにある記録は残す。受信スレッドは待たず、パケット writer の処理完了を待たず、次の UDP 受信を続ける。受信総数と通し番号は継続する。この動作はアプリケーションのログ待ちキューによる損失を局所化するが、OS やネットワーク上の UDP 損失を防止・保証するものではない。
- 集計カウンターは少なくとも受信総数、パケットログ enqueue 数、書き込み完了数、キュー満杯による破棄数、キュー深度・bytes の現在値と最大値を持つ。TUI は受信総数、記録済み数、アプリのログキュー破棄数、キュー深度を示す。
- OS の UDP 受信破棄数はアプリのログキュー破棄数と別カウンターにする。OS またはソケット API から数値を取得できる環境では取得値を示し、取得手段がない環境では `取得不可` とする。送信側の番号欠落から OS 損失数を推定しない。終了サマリーにも OS カウンター値または取得不可、アプリのログキュー破棄数を別々に記録する。
- ログキュー破棄が発生した場合は件数を集計し、間隔を空けた警告または終了サマリーとしてイベントログだけに `[warn] Warning: packet log queue overflow; discarded <件数> packet logs` を記録する。受信ごとに警告を出してイベントログや TUI を飽和させない。パケットログには警告を含めない。
- 一般の運転条件でもネットワーク・OS・プロセス停止などによる UDP 損失は起こり得る。本仕様が保証するのは、受信スレッドがログ書き込みや UI 描画を待たないこと、およびアプリのログキュー満杯時に既存記録を保持して新着記録の破棄を計数することまでである。

## 8. イベント、送信、エラーログ

- 送信、エラー、警告、起動・終了など、受信データグラム記録以外の全イベントをパケットログとは別のイベントログに記録する。既定の行頭はパケットログと同じくローカル時刻ミリ秒と小文字ログレベルを使う。
- 送信成功行は `Transmitted(<バイト数>): <IPv4宛先>:<ポート>` の形式とし、時刻はローカル UDP ソケットの送信完了時刻とする。例: `[2026-08-18 12:34:56.789] [info] Transmitted(4): 127.0.0.1:5001`。
- 送信エラーは `[error] Error: UDP send failed (<バイト数> bytes to <宛先>): <エラー内容>` の形式とする。エラー行にも送信予定サイズと時刻を含める。
- 起動、bind 成功、TUI の送信開始・ファイル完了、キュー停止、終了は `[info]`、異常や送信失敗は `[error]`、受信サイズ超過・ログ破棄は `[warn]` でイベントログに記録する。
- イベントログ、TUI の状態表示、標準出力・標準エラー出力には UDP ペイロード、hex、base64、入力行の生テキストを記録しない。必要な診断情報は時刻、サイズ、宛先、ファイルパス、行番号、件数、OS のエラー内容に限定する。
- 全ログ行は 1 行とし、エラーメッセージに改行が含まれる場合は空白へ置き換える。
- パケットログ writer とイベントログ writer はそれぞれ専用スレッドとし、受信スレッド・送信 worker・Textual ループにファイル I/O を行わせない。パケットログ writer は受信キューを FIFO で drain し、イベント writer は運転イベントを順次書く。受信サイズ超過やログキュー溢れは受信ごとに enqueue せず、一定間隔で集約する。
- イベントログ待ちキューは最大 4,096 件とする。受信スレッドからの受信エラー・受信サイズ超過・ログキュー警告は待たずに enqueue し、イベントキューが満杯ならイベント行を破棄して件数を集計し、終了時に警告とサマリーへ含める。このためイベントログの飽和中は個々の受信警告・一時エラーがすべて保存されるとは限らない。送信 worker からの通常イベントはイベント writer の空きを待ち、送信 worker にバックプレッシャーをかける。パケットログキューと受信件数には影響しない。
- 2つの writer は各行の直後には flush せず、最大 1 秒ごと、または 256 行を書いた時点の早い方で flush する。終了時は保留行をすべて出力して flush し、ファイルを閉じる。これにより受信処理の I/O 待ちを避け、行ごとの flush より書き込み回数を抑える。
- periodic `flush()` は Python のバッファから OS へ渡すものであり、`fsync` 相当の永続化を保証しない。異常終了や電源断では直近の flush 以降の行が失われる可能性がある。ログ内容のクラッシュ時耐久性より受信処理の継続性と書き込み効率を優先する。
- 終了時のイベントログには受信総数、パケットログ writer の書き込み完了数、アプリログキュー破棄数、イベントログキュー破棄数、OS 受信破棄数（取得不可を含む）、最終キュー深度を記録する。受信スレッド停止後にパケットログキューを drain し、カウンター確定後にサマリーをイベント writer へ渡してから両 writer を flush・終了する。

## 9. ログファイルの作成・追記

- 起動時刻の自動ファイル名は衝突しないよう連番で一意にする。
- JSON で明示した `packet_log_path` または `event_log_path` の既存ファイルには起動時から追記する。これにより、同じ指定パスを使う複数回の実行記録を保持する。
- 自動生成したログは一意な新規ファイルに記録する。両ログは専用 writer thread が最大 1 秒ごと、または 256 行ごとに flush し、正常終了時には保留行を出力して flush して閉じる。`flush()` は電源断時の永続化を保証しない。
- 追記は既存 `docs/specification.md` の指定パケットログに関する記述、および稼働をまたいでログを保持する要求に合わせた判断である。C++ 実装の `basic_file_sink_mt(path, false)` は既存ファイルを起動時に切り詰めるため、この点では C++ 実装より本仕様を優先する。
- 自動生成・指定を問わず、パケットログまたはイベントログを開けない場合はネットワーク処理を開始しない。

## 10. 終了と障害

- TUI の入力欄で `quit` を実行するか `Ctrl+C` を受けたら、TUI だけでなく Python プログラム全体を正常終了する。新しいコマンド・送信を開始せず、未処理キューを破棄する。進行中のローカル UDP 送信操作の完了を待ち、`/Wait` は中断して、現在のファイルを停止する。破棄したファイル数と停止したファイル・行をイベントログに記録する。送信ワーカーと受信スレッドを停止してソケットを閉じ、受信スレッドが停止した後に保留中の受信記録を packet writer が drain する。受信・記録・破棄カウンターを確定してイベントログへ終了サマリーを送り、両 writer が flush して閉じた後に終了する。
- bind、設定読み込み、ログファイル作成など起動時の致命的エラーは異常終了する。
- UDP 受信の一時エラーは 1 行をイベントログへ記録し、ソケットが利用可能なら受信を継続する。終了に伴うキャンセルはエラー扱いにしない。
- UDP 送信失敗は再送せず、現在のファイルを失敗終了して送信キューを一時停止する。利用者が `resume` を入力したら後続ファイルから再開する。
- パケットログ writer の書き込み失敗は記録を維持できない致命的エラーとして TUI、標準エラー出力、および稼働中のイベント writer の優先通知経路へ通知し、新しい送受信を停止して異常終了する。イベントログ writer 自体が失敗した場合は TUI と標準エラー出力へ通知して異常終了する。書き込みに失敗したレコードを保存済み件数に含めず、致命的な書き込み失敗後は保留キューの保存を保証しない。

## 11. 受け入れ基準

1. uv で Python 3.14 と実装時に固定した Textual 依存を選択して単一スクリプトを起動できる。Textual のバージョンを最新版と決めつけず、Windows・macOS・Ubuntu Linux で UI 起動と入力を確認する。
2. 既存 `examples/server-a.json` / `server-b.json` を編集せずにそのまま指定して起動できる。`ipc_port` は存在しても Python 版の動作に影響せず、Python 版追加キーは省略時に既定値を使う。
3. `send <file-path>` を繰り返し入力して複数ファイルを送信キューへ追加でき、送信中・受信中もコマンド入力が応答する。キューは FIFO で処理し、各ファイルはストリームで読み、`/Wait` は次の行より前に適用される。パス内空白と引用符の扱いは本書どおりである。
4. hex の大文字・小文字、途中の空白、コメント、空行、`/Wait`、不正文字、奇数桁、サイズ上限が本書の規則どおり処理される。
5. 別の UDP ピアから受信したデータについて、Textual に受信カウンターと時刻・サイズ・番号を含む概要が表示され、ログキューが満杯でない場合はパケットログに同じ時刻・番号・サイズと完全な大文字 hex が記録される。
6. `Transmitted` 成功ログに送信サイズと時刻があり、送信・エラー・その他のイベントはイベントログだけに記録され、パケットログには受信データグラム記録以外が含まれない。イベントログと Textual 画面に UDP ペイロードが含まれない。
7. ファイル内エラーで該当行を送信せず、ファイル名・行番号をイベントログに記録し、それ以前の送信済みデータグラムを取り消そうとしない。後続ファイルは保留し、`resume` 後に失敗ファイルを再送せず次のファイルから再開する。
8. バイト上限またはレコード数上限超過時に受信処理を待たせず、既存キューを残したまま到着中の記録だけを破棄する。特に 0 バイトデータグラムの連続受信でも件数上限でメモリ使用量を制限し、破棄数をイベントログだけに集計して後続受信を継続する。
9. 明示ログパスが既存なら追記し、両 writer が最大 1 秒ごとまたは 256 行ごとの早い方で flush する。終了時に保留記録と終了サマリーを flush する。パケットログとイベントログが同一パスなら起動前にエラーにする。
10. `status` と `help` が動作し、`quit` または `Ctrl+C` で未処理キューと現在ファイルを停止し、`/Wait` を中断する。保留受信ログを drain し、両ログを flush して終了する。終了は未処理キューの全ファイル完了を待たない。
11. 不在・読取不可のファイルパスや不正コマンドは送信キューへ追加せず、イベントログと Textual イベントパネルにエラーを出す。ファイル処理エラー後は `status` で一時停止状態を確認でき、`resume` で後続ファイルから再開できる。
12. 受信・送信中の状態更新とイベント表示がコマンド入力欄を消去・上書きせず、バックグラウンド処理から端末への直接出力がない。Textual への通知は容量 100 件、同時 callback 最大 1 件、最大 10 回/秒で集約され、受信総数・記録数・破棄数のカウンターは通知の集約後も正しい。イベント一覧は最大 100 行でスクロールでき、端末リサイズで再配置される。
13. 受信、packet writer、event writer、送信 worker が独立し、受信スレッドが hex 変換・ログ I/O・UI 描画をしないことを確認する。受信ログキューが詰まっても受信スレッドを待たせず、終了時に writer が保留記録を drain する。
14. 既定の `SO_RCVBUF` 要求値 4 MiB と設定可能値を bind 前に適用し、OS が返す有効値、または設定失敗・取得不可を TUI とイベントログに表示する。Windows・macOS・Linux で有効値が異なる可能性を受け入れ、OS UDP 受信破棄数はアプリログキュー破棄数と別表示する。終了サマリーに受信総数、ログ記録数、ログキュー破棄数、OS 受信破棄数または取得不可を含める。
15. ログ writer の書き込み失敗を検出して送受信を停止し、失敗レコードを保存済み件数へ加算せず、TUI と利用可能なエラー出力先に通知して異常終了する。

| --- | --- | --- | --- |
| 一つの Python スクリプトの送受信形態 | 要求は一つのスクリプトで送信・受信することを求めるが、同時動作か、モード選択かは明示されていない | 一つの UDP ソケットで受信を常時継続し、TUI から送信する同時動作とする | 送信のみ・受信のみのモード切り替えを必要とする場合は TUI の構成を変更する |
| Python 版と C++ 版の送信制御 | C++ 版は TCP ループバック IPC を使う。Python 版では TUI が同プロセスで送信を開始できる | Python 版は TCP IPC を実装しない。既存 C++ `udp_sender` は Python 版へ接続できない | C++ の既存送信クライアントから Python 版を制御する必要があれば、別途 TCP IPC 互換仕様が必要 |
| `ipc_port` | 既存サンプル設定には含まれるが、単一プロセス TUI に IPC は不要 | 既存 JSON をそのまま使えるよう任意キーとして読み飛ばす | 値の検証・警告を要求する運用があれば決める |
| パケットログに含める内容 | 要求は受信パケットログと別のイベント・エラー・送信ログを指定している | パケットログは受信データグラム行だけとし、警告を含む全イベントを別ログだけに記録する | なし |
| 指定ログの追記と flush | `docs/specification.md` は追記とする一方、C++ 実装は起動時に切り詰める。行単位 flush は受信処理の負荷を増やし得る | 指定パスは追記し、専用 writer が最大 1 秒または 256 行ごとに flush する。終了時も flush する | なし。C++ 実装との差と、flush 間隔中のクラッシュで直近行を失う可能性を受け入れる |
| 32,768 バイト超の受信 | C++ は 32,768 バイトの受信バッファだが、超過データグラムの正確なサイズ・切り詰め動作を明示していない | Python は IPv4 UDP データグラム全体を受け取り、超過も全体をパケットログへ記録し警告する | 受信も 32,768 バイトで拒否する必要があれば方針変更する |
| 0 バイト送信 | C++ IPC は長さ 0 を扱える一方、C++ 入力ファイルでは空行を無視するため表現手段がない | 空行は互換どおり無視し、TUI に 0 バイト専用操作を設けない | 0 バイトデータグラムが必要なら入力コマンドまたは UI 操作を追加する |
| ファイル内エラー後のキュー | C++ は最初のエラーでプロセス全体を異常終了する。TUI は対話継続と複数の逐次送信要求を扱う | 現在ファイルだけ失敗終了し、後続ファイルを保留する。`resume` の明示入力で次のファイルから再開する | なし |
| `/Wait` の数字中の空白 | C++ 実装は数値引数内の空白を除去し、例えば `1 2 3` を 123 と読む | 互換のため同じ挙動を規定 | 厳密な十進整数のみ許可する方針なら C++ との入力互換性を下げて変更する |

## 13. C++ 互換性の差異と対応

| 項目 | 既存 C++ 版 | Python 版の仕様 |
| --- | --- | --- |
| UDP 実行構成 | `udp_server` と `udp_sender` の二つの実行ファイル。TCP ループバック IPC を使用 | 一つのプロセスと一つの IPv4 UDP ソケット。受信スレッド、独立した送信 worker、Textual asyncio ループを使用。TCP IPC は実装しない |
| UDP 受信バッファ | 32,768 バイトの受信バッファ | `recvfrom(65535)` で IPv4 UDP の最大ペイロード 65,507 バイトを取得。32,768 バイト超も全量記録 |
| ソケット受信バッファ設定 | Python 版の `SO_RCVBUF` 要求・有効値表示はない | `receive_socket_buffer_bytes`（既定 4 MiB）を bind 前に要求し、OS が報告する有効値または設定エラーを記録。Windows/macOS/Linux の制限・値の報告差を許容 |
| 受信ログのキュー満杯 | C++ 仕様の上限超過時は保留ログ全体を消去する | バイト上限と件数上限を持つ。満杯時に今回の受信記録だけを破棄し、既存記録を維持。破棄数を計数する |
| 受信損失の監視 | アプリのログキュー警告を記録 | 受信総数、ログ enqueue/完了/破棄、キュー深度を監視する。取得可能な OS UDP drops とアプリのログキュー破棄を別計数し、取得不可を明示 |
| 受信ログ書式 | `[時刻] [info] Received(<size>): <number>: <HEX>` | C++ と同じ行書式、大文字 hex、時刻と番号の採取時点を維持。0 バイトの末尾形式も維持 |
| ログ出力と flush | C++ `spdlog` sink の挙動に従う | 専用 writer thread が書き込み、最大 1 秒または 256 行ごとに flush。終了時 flush。行ごとの flush よりスループットを優先し、クラッシュ時には直近 flush 後の行を失う可能性がある |
| ログファイルの起動時動作 | C++ 実装の sink は既存ファイルを切り詰める | 指定された既存ログへ追記する |
| 画面表示 | C++ sender/server は端末ログを出力 | Textual は受信概要とカウンターを最大 10 回/秒で集約表示し、直近イベント 100 行を保持。ログ書式・内容は UI 集約に左右されない |
| 送信構文と上限 | hex 行、`/Wait`、最大 32,768 バイト | 既存入力構文と上限を維持。送信ファイルを FIFO の単一 worker で処理 |

UDP の IPv4 アドレス、待受・送信先、送信サイズ上限、hex 入力行、`/Wait`、受信通し番号、受信ログ書式は `src/udp_sender.cpp`、`src/udp_server.cpp` および `docs/specification.md` を基準にする。受信キューの overflow 動作、全 IPv4 ペイロードを受け取るサイズ、`SO_RCVBUF` の設定、Textual UI 集約、flush 間隔、指定ログの追記は Python 版の明示的な差異である。受信ペイロード全体を記録するパケットログと、内容を含めずサイズを記録する送信・イベントログを分離する。
